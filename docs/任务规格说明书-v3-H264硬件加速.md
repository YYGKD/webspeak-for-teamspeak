### 0.1 相对 v2 草稿的关键纠偏

- v2 草稿曾将 H.264 **追加在 VP8 之后**（「不破坏既有 VP8 首选」思路）。审查已论证该顺序下 H.264 是死代码：mediasoup-client 对同 kind codec 只取列表中第一条本地支持的条目，VP8 所有浏览器都支持，排在后面的 H.264 永远轮空。**本规格锁定方案 A（H.264 在前），不接受「保持 VP8 在前」的折中**。
- v2 草稿未声明 H.264 的 `parameters`。缺省 `packetization-mode` 与 `profile-level-id` 会导致与浏览器上报的 H.264 能力（Chrome 默认 `packetization-mode=1`、`profile-level-id` 多档）匹配失败或落到非预期 profile，硬件编码路径随之落空。本规格按审查给出的参数集逐字段锁定。
- v2 草稿保留了捕获后的二次 `applyConstraints`（源自 P2P 时代的兼容性 workaround）。在 SFU + H.264 硬编场景下该调用代价被放大（管道重置 → 硬编会话重建；`max` 上限触发 libyuv CPU 下采样），必须移除。

## 1. 背景与目标

### 1.1 现状与问题

SFU v3 落地后，屏幕共享视频经 `MEDIA_CODECS` 中唯一的视频 codec `video/VP8`（`src/server/media-worker.ts:74-85`）协商上行。实测暴露两个性能瓶颈：

1. **VP8 软件编码 CPU 占用高**：Chrome 的 VP8 编码无 GPU 硬件加速路径（libvpx 纯软件实现）。1080p60 屏幕共享时发起端单进程 CPU 占用飙升，低端机器直接掉帧、发热降频；而 H.264 在 Windows（MediaFoundation/D3D11）、macOS（VideoToolbox）、Linux（VAAPI）均有成熟的 GPU 硬编路径。
2. **捕获流水线被二次 `applyConstraints` 打断**：`startScreenShare` 在 `getDisplayMedia` 返回后对视频轨再执行一次 `applyConstraints(videoConstraints)`（`useVoiceWebSocket.ts:3212-3221`）。该调用会重置 Chromium 的显示采集管道；当约束含 `max` 上限而源分辨率更高时，引入 libyuv CPU 软件下采样，帧链路出现「GPU 采集 → CPU 缩放 → 再上传 GPU 编码」的回读，与硬编目标直接冲突。

### 1.2 目标

1. Router codec 列表改为 **H.264 优先、VP8 兜底**：支持 H.264 硬编的客户端自动协商 H.264（GPU 编码，CPU 占用大幅下降）；不支持的客户端无需任何改动，自动落到第二项 VP8（行为与现状一致）。
2. 捕获流水线单段化：`getDisplayMedia` 一次性下发全部约束，移除二次 `applyConstraints`，消除管道重置与 CPU 软件下采样。
3. 推流参数固化为「保帧率」取向：`scalabilityMode: "L1T1"` + `degradationPreference = "maintain-framerate"` + `contentHint = "motion"`，保障 60fps 高刷场景。
4. TS3 语音链路、原生 TS6 P2P 路径、既有 SFU 分发逻辑（pipeToRouter 等）**零行为变化**。

### 1.3 非目标

- 不引入 Simulcast 或 SVC 多层（L1T1 即单层单时间档，见 §3 D4）。
- 不改动原生 TS 观众 P2P 路径的 codec 偏好（`preferScreenShareCodecs` 仍偏 VP8，仅服务 `ts-viewer-` 路径，见 §6.3）。
- 不引入 H.265/AV1；不在服务端做任何转码（mediasoup 为转发式 SFU，codec 由端侧协商）。
- 不改动 SFU v3 已定稿的分发、清理、信令语义，本规格仅替换/补充 codec 声明与捕获链路两处。

## 2. 协商机制背景（为什么顺序就是开关）

mediasoup 的 codec 协商为「Router 列表为 Offer、客户端能力为 Answer」的交集模型：

1. 服务端以 `MEDIA_CODECS` 创建 Router，`router.rtpCapabilities.codecs` 即按声明顺序输出；
2. 前端 `device.load({ routerRtpCapabilities })` 后，mediasoup-client 以本地 `RTCRtpReceiver.getCapabilities("video")` 与 Router 列表求交，**对每种 media kind 只保留第一条双方支持的 codec（`codecs[0]`）**，后续同 kind 条目仅在其 `rtcpFeedback`/参数兼容的子集场景下才可能保留，绝不作为首选；
3. `transport.produce()` 的 RTP 参数即由该交集生成，**第一条匹配项就是实际编码器**。

推论（审查审-1 的机制依据）：

- VP8 在前 → 交集第一条恒为 VP8（所有目标浏览器都支持 VP8）→ H.264 条目成为死声明，硬编永远不发生。
- **H.264 在前** → 支持 H.264 的浏览器第一条匹配 H.264（Chrome/Edge/Safari 均支持，桌面端默认走硬编）；不支持的浏览器（如部分无 H.264 编解码授权的 Linux Chromium 构建）第一条匹配落空，**自动顺延到第二条 VP8**——顺序本身即完整的优先级 + fallback 语义，无需任何前端特判代码。

## 3. 关键设计决策

### D1：方案 A —— H.264 置于 VP8 之前（审查锁定项）

排序即协商优先级（§2）。fallback 由「VP8 保留为第二项」天然实现：

- 客户端不支持 H.264 → 顺延 VP8，行为与当前线上完全一致（零回归面）；
- 客户端支持 H.264 但 GPU 硬编被驱动黑名单禁用 → Chrome 内部回落 OpenH264 软编，协商层无感知，仍优于或持平 VP8 软编；
- 服务端无需感知客户端选了哪个 codec——mediasoup 按 Producer 实际 codec 透传转发，pipeToRouter/Consumer 链路对 codec 透明。

**禁止**「VP8 在前 + H.264 在后」或「按客户端 UA 动态排序」：前者无效（§2），后者把协商正确性押在 UA 嗅探上，且 mediasoup-client 无 per-produce codec 选择入口之外的可靠覆写手段。

### D2：H.264 参数集锁定为 constrained baseline / packetization-mode 1

审查给定的参数集逐项依据：

- `"packetization-mode": 1`：NAL-unit 聚合/分片模式，Chrome 上报的 H.264 能力即 mode 1；声明缺省（=0）会与浏览器能力串不匹配导致该 codec 在交集中被丢弃。
- `"profile-level-id": "42e01f"`：constrained baseline profile、level 3.1。这是 WebRTC 生态互操作基线（RFC 7742 强制要求实现），所有浏览器的 H.264 能力必含该档；硬编路径对 baseline 支持最完整。
- `"level-asymmetry-allowed": 1`：允许收端以更高 level 解码，避免 level 精确匹配把高能力客户端挡在交集外。

不追求更高 profile/level（如 high profile）：WebRTC 屏幕内容 + 硬编兼容性取交集后，constrained baseline 是唯一安全默认值；码率天花板（§6.2，1080p ≥ 6 Mbps）已远高于 level 3.1 的名义上限，实际码率控制由拥塞控制与 `maxBitrate` 决定，不受声明 level 约束（`level-asymmetry-allowed: 1` 配合下）。

### D3：捕获约束单段下发，移除二次 `applyConstraints`

`getDisplayMedia({ video: videoConstraints })` 已携带全部约束（`useVoiceWebSocket.ts:3197-3203`，`width/height` 的 `ideal+max`、`frameRate` 的 `ideal+max`）。二次 `applyConstraints` 的初衷是「部分 Chromium 把 getDisplayMedia 约束当 hint」，但实测代价远超收益：

- **采集管道重置**：`applyConstraints` 触发 Chromium 重新配置 capturer，硬编会话随轨参数变化重建，共享开始瞬间出现卡顿/黑帧；
- **CPU 软件下采样**：源分辨率高于 `max` 上限时，Chromium 在采集链路内插入 libyuv 缩放，帧从 GPU 回读 CPU 缩放再上传编码，CPU 占用与本规格的硬编目标直接矛盾；
- **约束冗余**：`getDisplayMedia` 阶段下发的同一组约束已是生效口径，二次调用不产生新信息。

移除后分辨率兜底由两层既有机制承担：`max` 上限仍在首段约束中（Chromium 尊重与否都不影响功能正确性，仅影响上限严格性）；`encodings.maxBitrate` 码率天花板兜底链路预算（§6.2）。

### D4：单层单时间档（L1T1）+ 保帧率，面向 60fps 高刷

- `scalabilityMode: "L1T1"`：显式单层单时间档。VP8 默认可能协商出多时间档（L1T2/L1T3），H.264 下多层语义依赖 MRST 头扩展且硬编实现参差；锁定 L1T1 保证硬编路径最简、解码端无层级兼容风险。
- `degradationPreference = "maintain-framerate"`：带宽紧张时优先降分辨率/码率而非掉帧，与 `contentHint = "motion"`（用户选 ≥30fps 时）语义一致，服务「放视频/游戏」类高刷共享场景。

## 5. 服务端改动详述

### 5.1 `MEDIA_CODECS`：H.264 优先、VP8 紧随（审-1 锁定声明）

`src/server/media-worker.ts:65-86`，数组顺序调整为 **opus → H.264 → VP8**（opus 位置不变，保持音频语义零漂移）：
```ts
export const MEDIA_CODECS: readonly RouterRtpCodecCapability[] = [
  {
    kind: "audio",
    mimeType: "audio/opus",
    clockRate: 48000,
    channels: 2,
    preferredPayloadType: 111,
    rtcpFeedback: [{ type: "transport-cc" }, { type: "nack", parameter: "" }],
  },
  // 审-1：H.264 必须置于 VP8 之前。mediasoup-client 协商时对每种 kind
  // 只取列表中第一条本地支持的 codec（codecs[0]）：H.264 在前 → 支持
  // H.264 硬编的客户端优先命中；不支持者自动顺延第二条 VP8，无需前端特判。
  {
    kind: "video",
    mimeType: "video/H264",
    clockRate: 90000,
    parameters: {
      "packetization-mode": 1,
      "profile-level-id": "42e01f",
      "level-asymmetry-allowed": 1,
    },
    rtcpFeedback: [
      { type: "nack" },
      { type: "nack", parameter: "pli" },
      { type: "ccm", parameter: "fir" },
      { type: "goog-remb" },
      { type: "transport-cc" },
    ],
  },
  {
    kind: "video",
    mimeType: "video/VP8",
    clockRate: 90000,
    rtcpFeedback: [
      { type: "nack" },
      { type: "nack", parameter: "pli" },
      { type: "ccm", parameter: "fir" },
      { type: "goog-remb" },
      { type: "transport-cc" },
    ],
  },
];
```

- H.264 的 `parameters` 与 `rtcpFeedback` 为审查锁定值，逐字段依据见 §3 D2；**任何字段缺省或改写都需重新过审**（缺 `packetization-mode` 即协商失败，缺 `rtcpFeedback` 即丢包恢复/拥塞控制退化）。
- opus 与 VP8 两条既有声明逐字节保持不变：语音链路 SDP 语义零影响，VP8 作为 fallback 保留完整反馈能力。
- 该变更属 SFU v3 红线 #3 的允许项（既有 Worker 内 codec 声明扩展），不新增 Worker/进程/端口。

### 5.2 其余服务端逻辑零改动论证

- `mediaProduce` 分流（`voice-bridge.ts:1454` 分支）：判据为 `appData.mediaType` 与 `producer.kind === "video"`，与 codec 无关；H.264 Producer 与 VP8 Producer 走完全相同的路径。
- `pipeToRouter` / Consumer：mediasoup 对转发 codec 透明，PipeProducer 继承源 Producer 的 RTP 参数；观众端 `consume` 以其 `device.rtpCapabilities`（同样 H.264 优先交集）匹配 PipeProducer codec——发起/观众两端各自独立协商，**理论上存在发起端 H.264、个别观众不支持 H.264 的边界**：此时该观众的 Consumer 创建失败，`mediaConsume` 回错，前端按既有 `screenShareError` 路径提示。**该边界收敛依据**：发起端与观众端共享同一 Router codec 声明（H.264 优先），桌面浏览器 H.264 支持为事实全集，残余面仅为无 H.264 编解码授权的 Linux Chromium 构建——接受该残余风险并在 §10 验收中以真实浏览器矩阵覆盖，不为消边界引入转码层（红线 #5）。
- `speaker-producer-map.ts` 只订阅 audio，无行为变化（SFU v3 已论证）。

## 6. 前端改动详述（`useVoiceWebSocket.ts`）

### 6.1 移除二次 `applyConstraints`（审-3 第一项）

删除 `startScreenShare` 中 `getDisplayMedia` 成功后的整段二次约束（`useVoiceWebSocket.ts:3212-3221`）：
```ts
// ↓↓↓ 以下整段移除 ↓↓↓
      try {
        // Apply the cap once more after the browser's source picker returns.
        // Some Chromium versions treat getDisplayMedia constraints as hints
        // and only enforce the final capture size on the selected track.
        await videoTrack.applyConstraints(videoConstraints);
      } catch {
        // The selected source can still be shared when a browser refuses an
        // optional display-capture constraint; the actual settings remain
        // visible in the WebRTC diagnostics panel.
      }
```

- 移除依据见 §3 D3（管道重置 + libyuv CPU 下采样，与硬编目标直接冲突）。
- 首段 `getDisplayMedia({ video: videoConstraints, audio })`（:3205）保持不变，约束语义不丢。
- 其后的 `contentHint` 设置（:3226-3228，按 `maxFrameRate >= 30` 选 `motion`/`text`）**保留**：这是捕获端语义提示，不涉及管道重置。
- 诊断面板展示的 `videoTrack.getSettings()` 读数即实际生效值，无需 workaround 维持。

### 6.2 推流参数固化：L1T1 + maintain-framerate + 码率天花板（审-3 第二项）

`startScreenShareProducers`（:2680）的现有实现已满足审查要求，本规格将其从「实现事实」升级为「锁定规范」，改动仅限注释对齐，禁止后续退化：

```ts
const videoProducer = await client.produce({
  track: videoTrack,
  appData: { mediaType: "screen-video", streamId },
  encodings: [{
    maxBitrate: ceiling,          // screenShareBitrateCeiling(width, height)，1080p >= 6 Mbps
    scalabilityMode: "L1T1",      // 审-3 固化项（现 :2708）：单层单时间档，硬编最简路径
  }],
});
// 审-3 固化项（现 :2710-2717）：带宽紧张先降分辨率/码率，保帧率服务 60fps 高刷。
const sender = (videoProducer as unknown as { rtpSender?: RTCRtpSender }).rtpSender;
if (sender) {
  const params = sender.getParameters();
  params.degradationPreference = "maintain-framerate";
  await sender.setParameters(params);
}
```

- 三项叠加语义：`contentHint = "motion"`（捕获/编码器取向）+ `maintain-framerate`（拥塞降级取向）+ `L1T1`（层级结构）+ 高码率天花板，共同保证 1080p60 链路在带宽充足时跑满 60fps，紧张时降质不掉帧。
- 60fps 上限来源：`videoConstraints.frameRate.max`（:3202，由 `settings.maxFrameRate` 传入）；`encodings` 不再另设 `maxFramerate`，捕获帧率即推流帧率，避免双口径打架。
- `degradationPreference` 设置在 try/catch 内的现状保留（部分浏览器拒绝该键时静默忽略，不影响功能）。

### 6.3 P2P 路径 codec 偏好不动

`preferScreenShareCodecs`（:2800）仅服务原生 TS 观众的 P2P 路径（`ts-viewer-`），继续偏 VP8：原生 TS 客户端对 H.264 的支持矩阵不受本规格控制，SFU 链路 codec 与 P2P 链路互不影响，本规格不扩大改动面。

### 8.2 `scripts/media-worker-test.mjs:90-98` 断言更新（审-2 锁定）

将现「存在且仅存在 1 条 video/VP8 90000」断言整体替换为：

```js
const videoCodecs = MEDIA_CODECS.filter((codec) => codec.kind === "video");
const [firstVideo, secondVideo] = videoCodecs;
check(
  "MEDIA_CODECS 视频 codec 恰为 2 条：H.264 优先、VP8 紧随（审-1 顺序锁定）",
  videoCodecs.length === 2 &&
    firstVideo?.mimeType === "video/H264" &&
    secondVideo?.mimeType === "video/VP8",
  JSON.stringify(videoCodecs.map((c) => c.mimeType)),
);
check(
  "H.264 声明逐字段锁定：clockRate/parameters/rtcpFeedback",
  firstVideo?.clockRate === 90000 &&
    firstVideo.parameters?.["packetization-mode"] === 1 &&
    firstVideo.parameters?.["profile-level-id"] === "42e01f" &&
    firstVideo.parameters?.["level-asymmetry-allowed"] === 1 &&
    JSON.stringify(firstVideo.rtcpFeedback) === JSON.stringify([
      { type: "nack" },
      { type: "nack", parameter: "pli" },
      { type: "ccm", parameter: "fir" },
      { type: "goog-remb" },
      { type: "transport-cc" },
    ]),
  JSON.stringify(firstVideo),
);
check(
  "VP8 兜底声明完整：90000 + 完整 rtcpFeedback",
  secondVideo?.clockRate === 90000 &&
    JSON.stringify(secondVideo.rtcpFeedback) === JSON.stringify(firstVideo.rtcpFeedback),
  JSON.stringify(secondVideo),
);
```

### 8.4 真实浏览器验证（手工/半自动，验收必做）

脚本无法覆盖硬编真实性，以 Chrome `chrome://webrtc-internals` 为准：

1. 发起 1080p60 屏幕共享，检查 outbound-rtp：`encoderImplementation` 含 `Hardware`（Windows 常见 `MediaFoundation`/`D3D11` 字样）且 codec 为 H264；
2. 对照组：同机型改回 VP8（git stash 本规格改动），确认 CPU 占用显著高于 H.264 硬编组；
3. 共享开始后前 2 秒无黑帧/卡顿（二次 `applyConstraints` 移除后的管道重置回归检查）；
4. 模拟无 H.264 客户端（或临时在 Router 列表去掉 H.264 的对照构建）验证 VP8 fallback 出流正常。

## 11. 风险与残余边界

| 风险 | 评估与对策 |
|---|---|
| 部分 GPU/驱动被 Chrome 黑名单禁用 H.264 硬编 | 浏览器内部自动回落 OpenH264 软编，协商层无感知；功能正确，性能退化为与 VP8 同量级，可接受 |
| 无 H.264 编解码授权的 Linux Chromium 观看 H.264 流 | Consumer 创建失败 → 既有 `screenShareError` 提示路径；桌面 Chrome/Edge/Safari 不受影响（§5.2） |
| 移除二次 `applyConstraints` 后个别 Chromium 不尊重首段 `max` 上限 | 仅影响分辨率上限严格性，码率天花板仍兜住链路预算；实际分辨率经诊断面板可见，不构成功能缺陷 |
| `profile-level-id: 42e01f` 名义 level 3.1 与 1080p 高码率 | 声明 level 不约束实际编码输出（`level-asymmetry-allowed: 1` 配合下收端按更高 level 解码）；码率由拥塞控制与 `maxBitrate` 决定 |
