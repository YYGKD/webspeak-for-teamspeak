## О проекте

| Логика | Описание |
| --- | --- |
| **WHAT** | WebSpeak — самостоятельно размещаемый веб-клиент и голосовой шлюз для TeamSpeak 3 и TeamSpeak 6. |
| **WHY** | Пользователям не нужно устанавливать настольный клиент: достаточно открыть браузер, а оператор сохраняет контроль над сервером и данными. |
| **HOW** | После запуска настройте цель TeamSpeak и политику доступа в панели администратора. Браузер отвечает за интерфейс и аудио, WebSpeak — за шлюз. |

> **Производная версия**: этот репозиторий основан на [`EchoSixHIYA/WebSpeak-client-for-TeamSpeak`](https://github.com/EchoSixHIYA/WebSpeak-client-for-TeamSpeak) (базовая версия `v0.2.4`). Изменения в исходном коде начиная с `v0.2.5` и их даты перечислены в [CHANGELOG](../CHANGELOG.md); полное заявление — в [NOTICE](../NOTICE).

## 🧩 Расширенные функции

### WebRTC

Включается в **Панель администратора → Сервер → Расширенные настройки**. До включения задайте диапазон UDP-портов (по умолчанию `40000–40099`), откройте его в firewall и сохраните. При включённом WebRTC диапазон заблокирован; новые подключения используют WebRTC. Если сеть не может установить WebRTC (например, UDP/TCP блокирует firewall), интерфейс показывает понятную диагностику сети и рекомендацию повторить, а не переходит на аудиоканал через WebSocket. Для публичного доступа нужен HTTPS.

Медиа обслуживает встроенный движок **mediasoup** (единственный движок): говорящие публикуются и подписываются динамически по `clientId ↔ producerId ↔ consumerId`, без зарезервированных audio m-line и без ограничения числа слотов. Связанные переменные окружения необязательны:

- `MEDIASOUP_WORKER_BIN` — путь к бинарнику mediasoup worker; по умолчанию используется поставляемый предкомпилированный `vendor/mediasoup-worker/` с проверкой SHA256. Пакеты Release и Docker-образ уже его содержат.
- `WEBSPEAK_MAX_SPEAKERS` — число одновременно публикуемых говорящих в сессии (1–64, по умолчанию 32).
- `WEBSPEAK_MEDIA_PUBLIC_HOST` — публичный адрес медиа для прокси/проброса портов (записывается в `announcedAddress` ICE-кандидата); не задавайте, если адрес медиа совпадает с адресом прослушивания.

Диапазон портов нужно открыть как для **UDP, так и для TCP** (TCP — резервный путь ICE-over-TCP).

### Демонстрация экрана (центральная пересылка через SFU)

Демонстрация экрана между веб-зрителями идёт через **центральную пересылку mediasoup SFU** в шлюзе WebSpeak: демонстрирующий отправляет в шлюз **один** поток, а шлюз раздаёт его каждому зрителю по мере подписки. Поэтому рост числа зрителей **не** увеличивает исходящую полосу демонстрирующего, а прямое соединение между браузерами не требуется — всё работает и за симметричным NAT, в корпоративной сети или через мобильный хотспот.

- **Две дорожки**: видео экрана и системный звук (если в диалоге браузера отмечено «поделиться звуком») идут отдельными дорожками и синхронны у зрителя.
- **Кодек**: предпочтительно H.264 (аппаратное кодирование на GPU, низкая нагрузка на CPU), иначе VP8.
- **Разрешение и частота кадров**: в настройках доступны до 1080p и 60 FPS; захват никогда не превышает сам выбранный источник (для вкладки это её область просмотра). При нехватке полосы выбор зависит от источника: **демонстрация вкладки/окна сохраняет разрешение** (документы и код остаются читаемыми), а **демонстрация всего экрана при ≥30 FPS сохраняет частоту кадров** (видео и игры остаются плавными).
- **Сторона зрителя**: статус трансляции, число зрителей, громкость, полный экран и выход; до **32** веб-зрителей на одну трансляцию.
- **Панель производительности**: показывает размер захвата рядом с фактическим размером кодированного вывода, частотой кадров, битрейтом, потерями и причиной ограничения — так видно, где узкое место: захват, кодирование или сеть.

Взаимодействие с **нативным клиентом TeamSpeak 6** остаётся одноранговым: стороны соединяются напрямую по WebRTC/ICE (та же конфигурация ICE, что и для голоса — свой STUN и при необходимости внешний TURN), а WebSpeak отвечает только за авторизацию сессии, состояние трансляции и передачу SDP/ICE-сигналов — эти медиаданные он **не** переносит. При настроенном TURN медиа может идти через этот внешний сервис, но никогда через шлюз WebSpeak.

### Серверы STUN и TURN

Браузеры используют ICE-серверы, чтобы определить своё внешнее отображение (STUN) и при симметричном NAT или блокировке UDP перейти на ретрансляцию (TURN). Встроенный публичный STUN работает без настройки.

- **Админ-консоль (рекомендуется)**: карточка **Серверы STUN / TURN** на странице `/admin` → «Сервер». Можно вести сколько угодно записей STUN и TURN, **перезапуск не нужен**. Оставьте пустым, чтобы использовать переменные окружения (`WEBSPEAK_STUN_URLS` / `WEBSPEAK_TURN_URLS` / `WEBSPEAK_TURN_SECRET` / `WEBSPEAK_TURN_TTL_SECONDS`) — обновление ничего не меняет для существующего развёртывания.
- **Две схемы аутентификации TURN**: **статическое имя пользователя и пароль** (то, что предлагают большинство сторонних сервисов) и **общий секрет coturn REST** (секрет остаётся на сервере, при каждой загрузке страницы выдаются краткосрочные учётные данные). Пароли и секреты хранятся в базе как шифртекст AES-256-GCM; API сообщает только, сохранён ли он, а открытый текст в браузер не попадает.
- **Порядок — это предпочтение**: порядок списка — порядок, в котором пробуют браузеры; более надёжный сервер ставьте первым.
- **Важно**: статические учётные данные передаются каждому посетителю — это публикует многоразовую учётную запись ретранслятора, обязательно задайте квоту у провайдера. `turns:` (TURN через TLS) требует сертификат от **удостоверяющего центра, которому доверяет браузер**, с SAN, совпадающим с именем хоста; самоподписанные сертификаты отклоняются, так как браузеры доверяют только встроенному списку корневых сертификатов. Порт 53 блокируется браузерами — не используйте его.

### Ретрансляторы

Ретранслятор передаёт только TeamSpeak-трафик текущей сессии и не является VPN. В панели администратора добавьте один или несколько узлов, задайте имя, адрес и токен. Пользователь сможет выбрать прямое подключение или настроенный ретранслятор. Режим ретранслятора запускается отдельно и не предоставляет страницу посетителя или панель администратора.

Сервис ретрансляции встроен в WebSpeak и использует стандартные библиотеки Node.js; GOST, sing-box и другие прокси-фреймворки не требуются. Медиа WebRTC передаёт [mediasoup](https://mediasoup.org/) `3.27.1` (лицензия ISC); прежний движок werift выведен из эксплуатации и остаётся только как тестовый двойник в зависимостях для разработки. TeamSpeak работает через поддерживаемый проектом [SDK EchoSixHIYA/teamspeak-js](https://github.com/EchoSixHIYA/teamspeak-js).

## 🚀 Развертывание

| Способ | Подходит для |
| --- | --- |
| Docker Compose | Постоянного сервера и простых обновлений |
| Пакет Release | Запуска без Node.js и инструментов сборки |
| Из исходников | Разработки и настройки проекта |

> Docker не обязателен: собранный проект можно запускать напрямую под systemd (`ExecStart=node dist/index.js`, рабочий каталог — каталог развёртывания, данные в `data/`). Это подходит для хостов, где Docker запрещён. Обновление тогда — «собрать локально → заменить артефакты → перезапустить сервис».

### Docker Compose

```bash
git clone --depth 1 https://github.com/EchoSixHIYA/WebSpeak-client-for-TeamSpeak.git
cd WebSpeak-client-for-TeamSpeak
docker compose pull
docker compose up -d
```

После запуска откройте `http://<ваш-хост>:3040/admin`, войдите с `admin` / `admin`, сразу смените пароль и настройте TeamSpeak. Данные хранятся в volume `webspeak-data`. Не используйте `docker compose down -v`, если не хотите удалить базу и настройки.

### Пакет Release

Скачайте подходящий пакет Windows x64 или Linux x64 из [Releases](https://github.com/EchoSixHIYA/WebSpeak-client-for-TeamSpeak/releases/latest), распакуйте в отдельную папку и запустите `start-webspeak.cmd` или `./start-webspeak.sh`.

### Из исходников

```bash
npm ci --ignore-scripts     # пропускает postinstall mediasoup: бинарник worker поставляется в vendor/
npm run verify:worker       # проверяет SHA256 для vendor/mediasoup-worker/
npm run prepare:sdk
npm --prefix web ci
npm --prefix web run build
npm run build
npm start
```

Производственной среде **не нужна нативная зависимость транскодирования**: `@discordjs/opus` перенесён в `devDependencies` и используется только офлайн-тестами (для запуска тестов выполните `npm rebuild @discordjs/opus`). Полный набор регрессионных тестов запускается командой `npm test` — проверка worker плюс кодеки, карта говорящих, восходящий конвейер, аудиоустройства, SFU демонстрации экрана, сквозной тест, учётные данные TURN и конфигурация ICE, всего девять наборов.

## ⚠️ Требования и замечания

- Node.js `>=22.5` нужен для сборки из исходников; Docker и Release уже содержат необходимые компоненты.
- Нужен современный Chrome, Edge или другой браузер с WebRTC. Микрофон и звук окна обычно требуют HTTPS.
- WebSpeak должен иметь доступ к TeamSpeak; стандартный голосовой порт — `9987`.
- Веб-сервис использует `3040/TCP`; для публичного сайта направьте HTTPS и WebSocket через обратный прокси.
- Порты WebRTC по умолчанию `40000–40099` для UDP и TCP; откройте весь диапазон и отключите WebRTC перед изменением.
- Для IPv6 нужен маршрутизируемый IPv6, включённый IPv6 в ОС/контейнере и правила firewall. Литерал задаётся как `[2001:db8::1]#9987`.
- Одна сохранённая браузерная идентичность может использоваться только одним активным подключением.
- Фоновая музыка доступна только на компьютере и требует WebRTC.
